# ADR 013: Data layer: static catalog replay, sandbox as cross-check, client secrets

- Status: Accepted
- Date: 2026-10-23

## Context
FR-3.8 (Supabase RLS and grants), FR-3.9 (Firebase rules) and FR-3.10 (secrets in client code)
are Phase 3. PLAN.md describes applying migrations in a disposable network-less
`supabase/postgres` and running splinter-style catalog checks. A worker that starts Postgres
for every PR is slow and needs Docker on the worker. Most migrations only use DDL that a parser
can replay exactly.

## Decision
1. **Static first.** `authgraph.data.supabase` parses `supabase/migrations/*.sql` (filename
   order; `supabase/schemas/` if there are no migrations) with pglast (libpg_query). It replays
   them into a catalog of tables, RLS flags, policies, grants and revokes, default-privilege
   revokes and views. On that catalog it runs the checks `rls_disabled`, `policy_true_write`,
   `security_definer_view` and `null_fail_open`. Supabase's default grants to `anon` and
   `authenticated` are modelled. API-exposed schemas come from `supabase/config.toml`.
2. **Sandbox as cross-check.** `packages/sandbox` replays the same migrations in a
   `--network none` Postgres, adding the Supabase roles and `auth` helpers when the image lacks
   them. It reads `pg_class`, `pg_policies`, `has_table_privilege` and view dependencies, and
   reports the same exposure reasons. A differential test asserts static == real catalog on
   every Supabase fixture (14 trees). Probes (`SET ROLE anon`) are Phase 4 (FR-3.8b).
3. **Firebase.** A small tokenizer and parser handles `firestore.rules` / `storage.rules` (paths
   are single tokens), and a JSON walker handles `database.rules.json`:
   - `firebase_open` covers no condition, `true`, and the test-mode `request.time <
     timestamp.date(…)`. It is deterministic for writes and heuristic for reads, because
     world-readable catalogs are common.
   - `firebase_auth_only` covers a sign-in check only. It is heuristic and reported for writes
     only.
   - The resource includes the rules file, because one repository can deploy several projects.
4. **Secrets.** The detectors are service-role JWTs (decoded `role` claim), `sb_secret_`,
   `sk_live_`, PEM private keys, and secret-named env vars with client-bundle prefixes. A
   literal key is reported only in client code: a `"use client"` module, `.vue`, `.svelte` or
   `.html` files, or client directories that are not server ones. Values are never stored;
   findings carry a 12-character SHA-256 prefix for de-duplication.
5. **Diff.** Exposures are compared on (resource, role, reason) with operations unioned, and are
   reported when new or widened. One finding per (resource, reason) lists the roles. Secrets are
   compared on (kind, value hash), so moving a file never re-reports.

## Consequences
Data findings need neither Docker nor a database on the worker. The sandbox guards the static
model against drift and is where Phase 4's proof probes run. Not modelled statically:
- functions and `SECURITY DEFINER` RPCs;
- `ALTER TABLE … OWNER`;
- DDL generated by `DO` blocks.

These are left to the sandbox. Placeholders in rules paths (`<STORAGE_BUCKET>`) are kept
verbatim.
